# 记忆第二步：统一人物与增量写入

本次实现人物归属、记忆类型、事件状态、证据、版本与管理界面。召回排序、向量索引、摘要注入、上下文预算属于第三步。

## 使用

启动 `npm run server`，进入控制台「记忆」。

- **人物**：按唯一 QQ 号查看跨群、私聊的全部记录及带来源的别名。控制台是管理员视图，因此可以同时查看各范围的资料。
- **事件**：查看多人共同事件、约定与承诺；可记录待进行、进行中、完成或取消。
- **会话**：只看该会话可见的记录，以及后台进度、失败原因、记忆模型调用次数/token。点击「处理下一批新消息」可以立即处理一批积压或重试失败批次。
- 添加／编辑支持类型、主体 QQ 数组、标题、关联事件、可见范围、状态、固定与过期时间。「来源与变更」保留来源摘录和此前版本。

每个人只建立一个 `qq:<QQ号>` 实体。昵称不会用于推测合并身份；旧记录缺少 QQ 号时显示待确认身份，可逐条编辑主体为正确 QQ 号。多人事件只保存一条，以多个主体关联。机器人主体为 `bot`。

自动抽取默认保持来源会话范围。管理员可以把适合共享的记录改为全局或指定多个会话。**统一人物不等于自动公开私聊内容**。后台模型不能扩大范围或更新固定记录。

删除为逻辑删除：默认视图和聊天不可见，勾选「显示已删除／已替代／已过期」可审查历史；这不是物理擦除。固定记录也可以由管理员编辑或删除。

## 数据与迁移

`data/memory/v2.json` 为唯一写入源（设置 `QQ_AGENT_DATA_DIR` 时使用对应目录）。包括：

- `persons`：唯一 QQ 身份与带会话来源的别名；没有身份的历史资料使用单独 `legacy:` 实体。
- `records`：`fact / preference / interaction / relationship / event / commitment`，关联一个或多个主体。
- `sources`：来源会话、本地消息 ID、QQ 消息 ID、说话人、时间和原文摘录；与 `subjectIds` 分离。
- `evidence`：本人明确表达、他人转述、模型推断、人工确认或历史导入。程序会把缺少主体本人来源的 explicit 降为 reported，但语义判断仍依赖模型。
- `version / history`：修改前快照、时间和修改者。管理端提交 `expectedVersion`，避免旧页面或迟到的模型结果覆盖新修改。
- `jobs`：各会话独立的处理游标、成功时间、失败原因及记忆模型用量。

首次读取自动导入旧的 `group_<群>/<QQ>.json`、`private_<QQ>/<QQ>.json` 和旧单文件 `memberImpression`。原文件不变，同时复制到 `backups/before-v2-<时间>-<唯一标识>/`。成功生成 v2 后不会重复导入。旧印象保留原范围，标记 `legacy`，不编造消息证据。旧单文件的其他废弃字段仍留在原文件／备份中，不转换为未经确认的新事件。

迁移输入或 v2 JSON 损坏会报错，不能悄悄创建空库。备份复制失败会阻止迁移。回退时先停止程序并备份整个记忆目录，再恢复旧版本使用保留的旧文件；回退版本不会理解 v2 新增数据。

当前使用原项目部署兼容的 JSON 原子快照，不引入额外数据库运行时。一次写入先构建副本，验证整个批次，临时文件写完后 rename；记忆与游标一起提交。**同一数据目录只能由一个 QQ Agent 进程写入**。每次提交会复制并重写快照，数据量大时应迁移到事务数据库；当前不宣称支持多进程写入或数据库级掉电持久性。

## 写入流程

1. 已通过入口权限判断的消息照常存档；记忆处理不更改聊天已读状态。
2. 接收新消息、启动／恢复和配置更新时，为允许的会话安排后台任务，不依赖机器人是否回复。
3. 按本地消息 ID 从上次游标向后取一批，提供确定的说话人和有限的同会话已有记录供模型做更新判断。
4. 校验候选类型、主体、来源、目标版本和可修改范围。坏候选使整批回滚，保留游标。成功的空结果也会推进游标。
5. 提交记忆、来源与游标；相同内容／类型／主体／单会话范围的记录去重，逻辑删除的相同条目不会被重试复活。
6. 有积压则稍后处理下一批。失败至少等待 60 秒再试，错误显示在会话页；并发最多两个会话，同会话复用一个任务。

抽取输出只可修改同一来源会话、相同主体、未固定的有效记录。模型暂停期间／退出期间／会话撤出白名单后不提交结果。已经调用模型但解析失败的用量仍累计到该会话的记忆用量。

配置在「设置 → 记忆」：

| 字段 | 默认 | 含义 |
|---|---:|---|
| `memory.consolidateEnabled` | true | 保留原开关名称，现在控制自动增量抽取 |
| `memory.extractionIntervalMs` | 60000 | 每批间隔，最小 1000 毫秒 |
| `memory.extractionBatchSize` | 60 | 每批最多消息条数，范围 1–100 |
| `memory.useChatModel` | true | 跟随聊天模型；关闭后使用独立 provider/model |

旧 `consolidateMinIntervalMs`、印象条数阈值不再驱动处理。历史积压从尚未处理的最早存档开始分批提取，会产生额外模型用量。旧聊天成本看板仍按聊天 session 汇总，**记忆模型用量单独显示在记忆会话页**；模型不返回 usage 时无法获知 token 数。

为限制每次写入调用的大小：新消息每批最多约 18000 字符，单条取前 4000 字符；可更新旧记忆最多 60 条／14000 字符，固定记忆最多 30 条／6000 字符。长消息的余文仍在原始存档中，但本轮抽取不读取；已被消息存储上限裁剪的历史无法恢复。不保证从全部历史中检测到语义重复或矛盾。模型输出的语义准确性须在实际聊天中观察与纠正。

## 与 TencentDB-Agent-Memory 的关系

参考版本：`0468a2a5b50eaafc54758ed1e2e6609472e5b6ce`，默认分支 `feat/server_team`。

- [L1 记录与版本结构](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/0468a2a5b50eaafc54758ed1e2e6609472e5b6ce/MemoryCore/src/core/record/l1-writer.ts)
- [独立 MemoryCore 配置](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/0468a2a5b50eaafc54758ed1e2e6609472e5b6ce/MemoryCore/tdai-gateway.standalone.yaml)

借鉴原始记录 → 具体记忆 → 事件 → 人物资料分层。没有复制上游源码、安装上游服务或增加它的 SDK。这里的事件是版本化的多人档案，基本人物资料是有效 fact/preference/interaction 且有 explicit/admin 依据的可重建视图；尚未引入 LLM 长篇人物总结。

`MemoryStore` 提供与召回无关的存储契约；后续可增加 MemoryCore 适配器，但 QQ 主体、消息说话人和可见范围仍由本项目验证。当前没有声称提供完整的上游兼容适配器。

原提示词仍按当前相关成员选取最近三条有效事实类记忆，增加证据标签；事件不自动注入。`memory_query` 只列当前会话可见记录，提供 ID 和版本给写入工具使用。没有加入向量召回、语义检索或新的上下文管理机制。保存承诺不代表启动定时提醒。

```powershell

node test/memory-preview.mjs
```

测试和预览使用临时目录，不读取真实 QQ 消息或凭据。预览只启动本地 HTTP 控制台，使用虚构人物和事件，不连接 QQ、不调用真实模型、不启动遥测；终端 Ctrl+C 关闭。
